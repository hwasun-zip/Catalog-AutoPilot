# 🤖 Catalog AutoPilot
### Claude API 기반 이상탐지 원인 후보 자동 판단 & 리포팅 파이프라인

> Catalog Triage 프로젝트에서 SQL이 "숫자로는 이상하지만 원인을 확신할 수 없다"고 넘긴 케이스들을, AI가 브랜드·메뉴명 등 맥락을 이해해서 재판단하고 담당자가 바로 액션할 수 있는 리포트로 정리합니다.

**핵심 질문**: SQL이 통계적으로만 잡아낸 이상치 후보 중, AI가 판단할 것과 사람이 확인할 것을 어떻게 나눌 수 있을까?
---

## 📌 프로젝트 개요

이 프로젝트는 독립적인 분석이 아니라, **Catalog Triage(Project 1)의 후속 파이프라인**입니다.

**[Project 1: Catalog Triage]**
SQL로 32,199건의 가격 이상치 탐지 → High Confidence(10,500건, 자동확정) / Needs Review(21,699건, 원인불명) 분리

**[Project 2: Catalog AutoPilot] ← 본 프로젝트**
Needs Review 중 우선순위 상위 건을 Claude API로 재판단 → 오류 의심 / 정상 고가 추정 / 확신도까지 자동 산출 → 담당자용 액션 리포트 자동 생성

'문제를 발견한다(SQL) → 원인까지 판단하고 자동화한다(AI)'로 이어지는 구조를 통해, 통계 규칙만으로는 불가능한 맥락 기반 판단을 자동화 파이프라인에 결합했습니다.

## 🛠 사용 기술

| 영역 | 기술 |
|---|---|
| AI 판단 | Claude API (claude-haiku-4-5), Prompt Engineering |
| 자동화 | Python (배치 처리, 구조화된 JSON 출력 파싱) |
| 환경 | Google Colab |

## 🔍 왜 SQL만으로는 부족한가

Catalog Triage에서 Z-Score 기반 이상탐지를 적용했을 때, 통계적으로는 튀지만 실제로는 정상인 케이스(스테이크하우스의 고가 스테이크, 레스토랑의 고급 와인 리스트, 대용량 세트메뉴 등)가 다수 오탐되는 것을 확인했습니다. 이런 케이스는 **가격 수치만으로는 판단할 수 없고, 메뉴명·브랜드명이 담고 있는 맥락을 이해해야** 정확히 분류할 수 있습니다. 이 지점에서 LLM의 역할이 필요하다고 판단해 본 프로젝트를 설계했습니다.

## ⚙️ 파이프라인 설계

### 1. 대상 선정
21,699건 전체를 처리하는 대신, 실무처럼 **이상 정도(price_z_score)가 큰 순으로 우선순위를 매겨** 상위 건부터 처리하도록 설계했습니다. 이는 비용 효율성과 실제 운영 우선순위 원칙을 동시에 반영한 결정입니다.

### 2. 프롬프트 설계
Claude에게 단순히 "이상치인지 아닌지"를 묻지 않고, 아래 정보를 구조화해서 제공한 뒤 구조화된 JSON으로 응답받도록 설계했습니다.
- 메뉴 정보(상점명, 메뉴명, 카테고리, 가격, 카테고리 평균가, 배수)
- 판정(오류 의심 / 정상 고가 추정 / 판단 불가), 근거, 확신도(높음/중간/낮음)

### 3. 배치 처리 및 결과 검증

먼저 3건으로 API 호출과 JSON 파싱을 확인했습니다. 이 단계에서 1건(The Nutty Club)은 응답이 코드 블록(```json)으로 감싸져 파싱에 실패했고, 이후 30건 배치에서는 30건 모두 판정·근거·확신도가 정상적으로 추출되었습니다.

30건 배치 실행 후, 판정 분포와 확신도 분포를 확인하고 같은 메뉴명끼리 판정이 갈리는지 대조했습니다.

| 판정 | 건수 |
|---|---|
| 정상 고가 추정 | 21건 |
| 오류 의심 | 9건 |

| 확신도 | 건수 |
|---|---|
| 높음 | 22건 (73%) |
| 중간 | 8건 (27%) |
| 낮음 | 0건 |

확신도가 '중간'으로 나온 8건은 플래터, 다일(多日) 클렌즈 세트, 대용량 패키지("LARGE...PACKAGE")처럼 메뉴명에 묶음 힌트는 있지만 수량을 특정하기 어려운 경우가 대부분이었습니다. 다만 같은 메뉴(Rib Eye, 12oz - 44 ct Case, 6개 매장)에 대해 확신도가 '높음' 5건, '중간' 1건으로 갈려, 동일한 입력에도 확신도가 일정하지 않았습니다.

#### 사람 검토와의 대조

LLM 판정을 숨긴 채 30건을 직접 검토한 뒤 LLM 판정과 비교했습니다.

| 구분 | 건수 | 내용 |
|---|---|---|
| 일치 | 22건 | |
| 오류를 정상으로 판단 | 6건 | Rib Eye, 12oz - 44 ct Case (레스토랑 메뉴에 스테이크 44개 묶음으로 잘못 등록된 오류) |
| 정상을 오류로 판단 | 2건 | Gameday 100 Tender Meal (표기만 다른 같은 세트 메뉴, 같은 체인의 100 Tenders Game Day Meal은 정상 판정) |

불일치 8건 중 7건의 확신도가 '높음'이었습니다. **LLM은 틀릴 때도 확신도를 낮추지 않았으므로, 확신도만으로는 판정을 자동 확정할 수 없다**고 판단했습니다.

### 4. 액션 리포트 생성
판정과 확신도를 결합해 담당자가 바로 실행할 수 있는 권장 액션을 자동 부여했습니다.

| 권장 액션 | 기준 | 건수 |
|---|---|---|
| 즉시 수정 요청 (담당자 확인) | 오류 의심 + 확신도 높음 | 8건 |
| 검토 후 수정 | 오류 의심 + 확신도 중간 | 1건 |
| 참고용 - 사람 최종 확인 필요 | 정상 판정이지만 확신도 중간 | 7건 |
| 조치 불필요 | 정상 고가 추정 + 확신도 높음 | 14건 |

확신도가 '높음'인 판정도 사람 검토와 어긋났기 때문에, 즉시 수정 후보도 수정 전 반드시 담당자 확인을 거치도록 했습니다.

**한계**: 이 규칙은 LLM이 정상을 오류로 본 경우(Gameday 100 Tender Meal 2건)는 담당자 확인 단계에서 걸러낼 수 있지만, 오류를 정상으로 본 경우는 막지 못합니다. 실제로 놓친 Rib Eye 6건 중 확신도 '높음' 5건은 '조치 불필요'로 분류되어 담당자에게 전달되지 않았습니다.

### 5. 개선 및 재검증

위 한계를 줄이기 위해, 기존 30건에서 확인한 실수 2가지에만 근거해 개선을 적용했습니다.

| 기존 30건에서 확인한 실수 | 개선 |
|---|---|
| 레스토랑 메뉴에 도매 묶음 단위("44 ct Case")로 등록된 오류를 정상으로 판단 | 프롬프트에 판단 기준 추가: "ct Case" 같은 납품 단위는 오류 의심, "Group Meal 20"·"Platter"·"Package"·"Set" 같은 단체 주문은 정상 가능 (예시는 기존 30건에 나온 표현만 사용) |
| 같은 체인·같은 가격인데 표기만 다른 상품의 판정이 갈림 | 코드로 같은 체인·같은 가격의 판정 불일치를 찾아 사람 확인 대상으로 보냄 |

**검증 방법**
- 프롬프트 수정에 쓰지 않은 **새 검증 세트**를 따로 만들었습니다. Needs Review 31~500위에서 같은 메뉴·같은 가격 중복을 1건으로 줄인 뒤(241건) 시드를 고정해 30건을 무작위로 뽑았습니다.
- 새 검증 세트의 사람 판정(오류 6건, 정상 24건)은 **AI를 실행하기 전에 확정**했습니다.
- 개선 전·후 모두 같은 모델(claude-haiku-4-5)과 같은 설정으로 실행하고, 프롬프트와 일관성 검사만 다르게 했습니다.

**결과**

| 지표 | 새 검증 세트 전 → 후 | 기존 세트 전 → 후 |
|---|---|---|
| 사람 판정과 일치 | 27 → 27 / 30 | 22 → 24 / 30 |
| 오류가 확인 없이 통과('조치 불필요') | **1 → 0** | 6 → 0 |
| 정상을 오류로 판단 | **2 → 0** | 2 → 0 |
| 오류를 정상으로 판단 | 1 → 2 | 6 → 0 |
| 판단 불가 | 0 → 1 | 0 → 6 |
| 사람이 확인할 건수 | 16 → 21 | 14 → 19 |
| 일관성 검사가 사람 확인으로 보낸 건수 | 0 | 0 |

- 기존 세트의 개선 전 재실행에서도 Rib Eye 44 ct Case 6건이 다시 모두 '정상 고가 추정 / 확신도 높음'으로 나와, 처음 발견한 실수가 재현되는 것을 확인했습니다.
- 새 검증 세트에서는 프롬프트 수정에 쓰지 않은 도매 묶음 메뉴(Sirloin Steak, 6oz – 84 ct Case)를 개선 후 '오류 의심 / 높음'으로 잡아, 확인 없이 통과하던 오류가 0건이 되었습니다. 정상 메뉴를 오류로 본 2건(Box Lunch, DELUXE EASY MEAL)도 사라졌습니다.
- **부작용**: 개선 후에는 단품 메뉴 오류를 덜 단정했습니다. 새 검증 세트에서 Turkey "Cali Fresh", T-bone & eggs는 '정상 고가 추정 / 중간', Jason은 '판단 불가'로 바뀌었고, 기존 세트에서도 원래 잘 잡던 단품 오류 6건이 '판단 불가'로 바뀌었습니다. 확신도 '중간' 이하는 사람 확인으로 보내는 규칙 덕분에 놓치지는 않았지만, 사람이 확인할 건수가 새 검증 세트 기준 16건에서 21건으로 늘었습니다.
- 일관성 검사는 두 세트 모두에서 한 번도 작동하지 않아 효과를 확인하지 못했습니다.
- 30건 규모이고 같은 입력에도 응답이 조금씩 달라질 수 있어, 1~2건 차이는 우연일 수 있습니다.


## 💡 핵심 성과 및 배운 점

- SQL(통계)과 LLM(맥락 이해)의 역할을 분리하여, 각각의 강점을 살리는 하이브리드 파이프라인을 설계했습니다. 예를 들어 Nusr-Et(유명 스테이크하우스)의 고가 스테이크는 LLM이 브랜드 인지도를 활용해 정상으로 정확히 판별했습니다.
- 전수(21,699건) 처리 대신 우선순위 기반 샘플링을 적용해 비용과 시간을 실무적으로 관리했습니다.
- Confidence(확신도) 필드를 응답에 포함시켜 "바로 조치할 후보"와 "사람이 판단해야 하는 것"을 나누는 워크플로우를 설계했습니다. 이는 Project 1의 신뢰도 등급화(High Confidence / Needs Review) 설계 철학과 일관됩니다.
- 사람 검토와 대조한 결과 30건 중 22건이 일치했고, 불일치 8건 중 7건이 확신도 '높음'이었습니다. LLM이 스스로 매긴 확신도는 정확도를 보장하지 않는다는 것을 확인했고, 그래서 즉시 수정 후보에도 담당자 확인을 남겼습니다.
- 발견한 실수에만 근거해 개선하고, 수정에 쓰지 않은 30건으로 다시 측정했습니다. 확인 없이 통과하던 오류는 1건에서 0건으로 줄었지만, 단품 오류를 덜 단정하는 부작용으로 사람이 확인할 건수는 16건에서 21건으로 늘었습니다.

## 🔮 향후 개선 방향

- 현재 30건 단위로 검증했으며, 전체 21,699건으로 확장 시 비용·시간 추정 및 배치 최적화가 필요합니다.
- 개선 후 단품 메뉴 오류를 '판단 불가'나 '정상 / 중간'으로 미루는 경향이 생겼습니다. 단품 메뉴에 대한 판단 기준을 별도로 검토하되, 새 검증 세트가 아닌 별도의 데이터로 수정해야 합니다.
- 같은 체인·같은 가격 일관성 검사는 이번 두 세트에서 작동하지 않았습니다. 같은 상품이 여러 매장에 등록된 경우가 많은 구간에서 효과를 확인해야 합니다.
- 30건 규모라 1~2건 차이는 우연일 수 있어, 같은 조건으로 여러 번 실행해 결과가 유지되는지 확인이 필요합니다.
- Slack/이메일 자동 발송 기능을 추가하면 리포트 생성부터 담당자 알림까지 완전 자동화할 수 있습니다.
- 이미지 품질 자동 검증(OpenCV 기반)을 결합하면 카탈로그 품질 이상탐지 범위를 텍스트/가격 외 시각 정보까지 확장할 수 있습니다.
